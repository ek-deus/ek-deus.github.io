Когда «не работает сеть», полезно проверять её по слоям: адресация, локальная связность, маршрут, DNS, порт и приложение. Так проще определить, на каком этапе перестают проходить пакеты.

## Порядок диагностики

```text
Адрес и интерфейс → шлюз и локальный сосед → внешний IP
                     ↓
       DNS → TCP-порт → TLS/HTTP → приложение
                     ↓
             захват пакетов
```

Успешный `ping` не подтверждает доступность TCP-порта или корректную работу приложения. И наоборот: отсутствие ICMP-ответа не всегда означает, что сервис недоступен.

## Адресация и шлюз

Сначала проверьте, получил ли компьютер адрес и есть ли маршрут к нужной сети.

```bash
# Linux
ip -br addr
ip route

# macOS
ifconfig
netstat -rn
```

```powershell
# Windows
ipconfig /all
```

Проверьте адрес интерфейса, маску и шлюз по умолчанию. В Linux строка `default via ...` в `ip route` показывает маршрут по умолчанию. Без него или другого подходящего маршрута компьютер обычно не сможет отправлять трафик во внешние сети.

Признаки, требующие проверки:

- Адрес `169.254.x.x` часто означает, что компьютер не получил IPv4-адрес по DHCP и назначил link-local адрес самостоятельно. Проверьте DHCP, Wi-Fi или кабель.
- Нет маршрута `default` — проверьте конфигурацию сети и наличие альтернативных маршрутов.
- Адрес и маска не соответствуют ожидаемой схеме — проверьте маску, шлюз и маршруты. Разные подсети сами по себе не исключают связь: между ними может маршрутизировать роутер.

### Проверка соседей по ARP

В локальной IPv4-сети ARP сопоставляет IP-адрес соседа с MAC-адресом. Записи соседей можно посмотреть так:

```bash
# Linux
ip neigh show

# macOS и Windows
arp -a
```

Пример Linux:

```text
192.168.1.1 dev eth0 lladdr 00:1a:2b:3c:4d:5e REACHABLE
```

- `REACHABLE` — сосед недавно подтверждал доступность.
- `STALE` — запись есть, но давно не подтверждалась; это само по себе не ошибка.
- `INCOMPLETE` — адрес ещё разрешается.
- `FAILED` — попытки разрешить адрес соседа не удались.

Если шлюз находится в непосредственно подключённой сети, но его MAC-адрес не разрешается, проверьте интерфейс, VLAN, Wi-Fi, кабель и доступность шлюза. Состояние `FAILED` указывает на неудачное разрешение соседа, но само по себе не определяет неисправный компонент.

## Проверка связности: ping и traceroute

`ping` отправляет ICMP Echo Request и показывает, пришли ли ответы и сколько заняла передача.

```bash
# Linux и macOS
ping -c 4 192.168.1.1
ping -c 4 8.8.8.8
ping -c 4 example.com
```

```powershell
# Windows: по умолчанию отправляет четыре запроса
ping 192.168.1.1
ping 8.8.8.8
ping example.com
```

Проверяйте последовательно:

1. Адрес шлюза — отвечает ли локальный маршрутизатор.
2. Внешний IP-адрес — есть ли IP-связность без участия DNS.
3. Доменное имя — разрешается ли имя и отвечает ли узел на ICMP.

Смотрите на потери и время ответа. Многие серверы и межсетевые экраны ограничивают или блокируют ICMP, поэтому отсутствие ответа не доказывает, что TCP-сервис недоступен.

`traceroute` показывает промежуточные узлы, которые отвечают на диагностические пакеты:

```bash
# Linux (пакет traceroute) и macOS
traceroute 8.8.8.8

# Linux, если установлен tracepath
tracepath 8.8.8.8
```

```powershell
# Windows
tracert 8.8.8.8
```

Звёздочки на отдельном промежуточном узле при ответах от следующих узлов обычно означают, что этот маршрутизатор не отвечает на диагностические запросы. Они не доказывают потерю транзитного трафика. Устойчивый рост задержки до конечного узла может указывать на проблему на пути, но по одному traceroute нельзя точно определить её место.

## DNS: проверка разрешения имён

Если IP-адрес доступен, а доменное имя не открывается, проверьте, какой резолвер использует система и что он возвращает. Подробное устройство DNS-записей разобрано в статье [«Настройка DNS для почты и сайта»](https://bigmike.help/ru/posts/008/).

### Какой DNS-сервер использует система

```bash
# Linux с systemd-resolved
resolvectl status

# Другие Unix-подобные системы — с оговоркой, что файл может быть сгенерирован системой
cat /etc/resolv.conf
```

```powershell
# Windows
ipconfig /all
```

В Linux с `systemd-resolved` проверьте DNS-серверы и настройки конкретного интерфейса: могут применяться разные DNS для разных доменов и сетей.

### Системный запрос и подробный ответ

```bash
# systemd-resolved
resolvectl query example.com

# dig показывает DNS-запрос и ответ
dig example.com
```

У `dig` в строке `status` обычно будет `NOERROR` при успешном ответе, `NXDOMAIN` — если сервер сообщает, что такого имени нет, или `SERVFAIL` — если сервер не смог обработать запрос. В `ANSWER SECTION` указаны записи и TTL; `SERVER` показывает, кто ответил.

```bash
# Только адреса из ответа
dig +short example.com

# Запрос конкретному DNS-серверу
dig @8.8.8.8 example.com
```

```powershell
# Доступно в Windows и macOS
nslookup example.com
nslookup example.com 8.8.8.8
```

`NXDOMAIN` — ответ об отсутствии имени, а не доказательство неисправности или подмены. Если так отвечает на имя, которое должно существовать, проверьте написание, авторитетную DNS-зону и ответы другого резолвера.

Если один резолвер отвечает, а другой нет, это повод проверить настройки локального DNS, роутера или провайдера. Запросы к публичным DNS могут блокироваться политикой сети. Разные адреса в ответах могут быть нормальными для CDN, географической балансировки и split DNS; сравните тип записи, TTL и авторитетные ответы.

## Проверка портов и локальных служб

Узел может отвечать на `ping`, но нужная служба при этом может быть недоступна. Проверьте TCP-порт с клиентской машины:

```bash
nc -zv -w 5 example.com 443
```

`-z` проверяет соединение без передачи данных, `-v` включает подробный вывод, `-w 5` задаёт таймаут. Текст результата зависит от реализации `nc` (например, OpenBSD или traditional).

В Windows используйте PowerShell:

```powershell
Test-NetConnection example.com -Port 443
```

`TcpTestSucceeded : True` означает, что TCP-соединение установлено. `telnet example.com 443` тоже может проверить установку TCP-соединения, но для TLS-протокола не покажет полноценный прикладной ответ.

Ошибки — ориентиры, а не безусловные доказательства:

- `Connection refused` обычно означает, что порт закрыт или служба не слушает его; такой ответ также может вернуть межсетевой экран с правилом REJECT.
- `Connection timed out` означает, что за время ожидания ответ не пришёл. Причиной могут быть фильтрация, потеря пакетов или недоступный узел.
- `No route to host` указывает на отсутствие маршрута либо на сетевой отказ, возвращённый промежуточным узлом.

### Что слушает локальная машина

На Linux проверьте слушающие сокеты командой `ss`:

```bash
sudo ss -tulpn
```

`-t` и `-u` выбирают TCP и UDP, `-l` — слушающие сокеты, `-n` — числовые адреса и порты, `-p` — процесс. Для сведений о чужих процессах обычно нужны права root.

```text
tcp LISTEN 0 4096 0.0.0.0:22 0.0.0.0:* users:("sshd",pid=812,fd=3)
```

Адрес привязки важен: `127.0.0.1:5432` принимает соединения только с этой машины, а `0.0.0.0:22` — на всех IPv4-интерфейсах. Для IPv6 проверьте отдельную привязку и настройки dual stack.

В Windows:

```powershell
netstat -ano
```

Состояние `LISTENING` означает, что локальный TCP-порт ожидает соединений; PID процесса указан в последнем столбце.

Если служба слушает нужный адрес, но подключение снаружи не проходит, последовательно проверьте host firewall, облачную группу безопасности, сетевой ACL и NAT/port forwarding, если сервер за роутером.

## Маршрут, сканирование портов и HTTP

### mtr: потери и задержки по маршруту

`mtr` многократно измеряет путь до узла и показывает статистику по каждому переходу. Это помогает увидеть нестабильность, которую можно не заметить при одном запуске traceroute.

```bash
# Debian / Ubuntu
sudo apt install mtr-tiny

# macOS с Homebrew
brew install mtr

# Интерактивный режим и отчёт на 100 циклов
mtr example.com
mtr -rwc 100 example.com
```

Поля отчёта включают число отправленных проб, потери, среднюю и максимальную задержку и её разброс. Потери только на промежуточном узле при отсутствии потерь до конечного адреса обычно связаны с ограничением ответов самого узла. Если потери видны и на конечном адресе, это может указывать на проблему на маршруте, но `mtr` не локализует её однозначно. Высокий `StDev` — повод повторить измерения и проверить нагрузку, а не самостоятельное доказательство перегрузки.

Если ICMP ограничен, можно попробовать TCP-пробы на нужный порт:

```bash
mtr -T -P 443 example.com
```

### nmap: состояние портов

`nmap` проверяет порты и определяет их состояние. Сканируйте только свои узлы или системы, на которые у вас есть разрешение. Для тестов проект nmap предоставляет `scanme.nmap.org`.

```bash
# По умолчанию — распространённые TCP-порты
nmap scanme.nmap.org

# Только указанные порты; определить версию службы на 443
nmap -p 22,80,443 example.com
nmap -sV -p 443 example.com

# Обнаружить активные узлы локальной сети без сканирования портов
nmap -sn 192.168.1.0/24
```

- `open` — порт принимает соединения.
- `closed` — узел ответил, что порт закрыт.
- `filtered` — сканер не смог определить состояние, часто из-за фильтрации.

### curl: HTTP, TLS и время этапов

`curl` показывает, что отвечает веб-сервер, и помогает отделить проблемы DNS, TCP, TLS и HTTP.

```bash
# Только заголовки ответа (запрос HEAD)
curl -I https://example.com

# Подробности соединения, TLS и заголовков
curl -v -o /dev/null https://example.com

# Запросить URL с конкретного IP, сохранив Host и TLS SNI
curl -I --resolve example.com:443:203.0.113.10 https://example.com
```

`-I` отправляет `HEAD`; некоторые серверы обрабатывают `HEAD` иначе, чем `GET`. При расхождении проверьте обычный GET-запрос. Не публикуйте вывод `curl -v` без проверки: в нём могут оказаться cookies, токены и другие чувствительные заголовки.

Чтобы пройти перенаправления, добавьте `-L`. Для замеров используйте `--write-out`:

```bash
curl -o /dev/null -sS -w 'DNS: %{time_namelookup}s  TCP: %{time_connect}s  TLS: %{time_appconnect}s  TTFB: %{time_starttransfer}s  total: %{time_total}s  HTTP: %{http_code}\n' https://example.com
```

Большое `time_namelookup` указывает на задержку разрешения имени; разница между `time_appconnect` и `time_connect` включает TLS-рукопожатие; высокий TTFB при быстрой установке соединения может указывать на задержку обработки запроса сервером.

Больше примеров — в статье [«curl для начинающих»](https://bigmike.help/ru/devops/017/).

## Захват и анализ трафика

Если адресация, DNS и подключение к порту выглядят исправно, но приложение получает `connection reset by peer` или `TLS handshake failed`, захват пакетов поможет увидеть, на каком этапе соединение ломается.

### tcpdump: захват пакетов

Список интерфейсов и захват трафика на Linux:

```bash
sudo tcpdump -D
sudo tcpdump -ni eth0 host 203.0.113.10
sudo tcpdump -ni eth0 tcp port 443
sudo tcpdump -ni eth0 port 53
```

`-n` отключает преобразование адресов и портов в имена. Укажите правильный интерфейс: на сервере с VPN, контейнерами или несколькими сетевыми картами трафик может идти не через `eth0`.

Сохраните ограниченный захват в pcap:

```bash
# Завершить после 1000 пакетов
sudo tcpdump -ni eth0 -c 1000 -w /tmp/capture.pcap

# Файлы по 60 секунд, хранить не более 10 файлов в ротации
sudo tcpdump -ni eth0 -G 60 -W 10 -w '/tmp/capture-%Y-%m-%d_%H-%M-%S.pcap'
```

Значение snaplen по умолчанию зависит от версии и платформы. Захват может содержать чувствительные данные: ограничивайте BPF-фильтр, права доступа к pcap и срок хранения. На Linux `-i any` позволяет захватывать трафик с нескольких интерфейсов, но формат захвата может отличаться от захвата на конкретном интерфейсе.

Фильтры `host`, `port`, `tcp`, `udp`, а также сочетания `and`, `or`, `not` — это BPF-фильтры захвата: пакеты, которые им не соответствуют, в файл не попадут.

### sngrep: SIP-диалоги

`sngrep` группирует SIP-пакеты в диалоги и показывает обмен сообщениями вроде `REGISTER`, `INVITE`, `180 Ringing` и `200 OK`.

```bash
sudo apt install sngrep
sudo sngrep
sudo sngrep port 5060
sngrep -I /tmp/capture.pcap
```

Команда `sngrep port 5060` предполагает незашифрованный SIP на стандартном порту. Для SIP-TLS и нестандартных портов настройте фильтр соответственно. В интерфейсе выберите диалог и нажмите Enter, чтобы открыть последовательность сообщений.

### Wireshark: разбор pcap

Захватите трафик на сервере, скопируйте файл на рабочую станцию с Wireshark и откройте его:

```bash
scp user@server:/tmp/capture.pcap .
wireshark capture.pcap
```

Примеры фильтров отображения Wireshark:

- `http.request` — HTTP-запросы;
- `tls.handshake` — сообщения TLS-рукопожатия;
- `dns` — DNS-запросы и ответы;
- `tcp.flags.reset == 1` — TCP-сегменты с флагом RST;
- `ip.addr == 203.0.113.10` — пакеты с указанным IPv4-адресом.

`Follow → TCP Stream` собирает данные одного TCP-соединения в последовательный поток. Не путайте фильтры захвата tcpdump (например, `port 443`) с фильтрами отображения Wireshark (например, `tls.handshake`): у них разный синтаксис и назначение.

### Какой инструмент выбрать

| Инструмент | Для чего | Где использовать |
|---|---|---|
| `ping`, `traceroute` | базовая связность и путь | рабочая станция или сервер |
| `dig`, `resolvectl` | диагностика DNS | система с проблемой или DNS-узел |
| `nc`, `Test-NetConnection` | проверка TCP-порта | клиентская машина |
| `ss`, `netstat` | локальные слушающие сокеты | сервер или рабочая станция |
| `mtr`, `nmap`, `curl` | маршрут, порты и HTTP | только разрешённые системы |
| `tcpdump`, `sngrep`, `Wireshark` | захват и разбор пакетов | сервер и рабочая станция |

## Краткий итог

1. Проверьте адрес, маску, интерфейс и маршруты: `ip -br addr`, `ip route`, `ipconfig /all`.
2. Проверьте локальную связность и шлюз: `ip neigh`, `arp -a`, `ping`.
3. Разделите DNS и сетевую доступность: `dig`, `resolvectl query`, `nslookup`.
4. Проверьте нужный порт и локальный слушающий адрес: `nc -zv`, `Test-NetConnection`, `ss -tulpn`.
5. Исследуйте маршрут и ответ приложения: `traceroute`, `mtr`, `nmap`, `curl`.
6. Если причина не видна, ограниченно захватите трафик через `tcpdump` и изучите pcap в Wireshark.

Сканируйте только системы, на которые у вас есть разрешение. Передача и хранение pcap требуют контроля доступа и срока хранения.
