В манифесте **Deployment** в Kubernetes есть несколько критически важных параметров и блоков, без которых приложение не сможет корректно работать, масштабироваться и проходить обновления в продакшене.

Вот ключевые секции и параметры, на которые всегда нужно обращать внимание:

### 1. Метаданные и количество реплик (`metadata` & `replicas`)

- **`replicas`**: Количество одновременных копий (подов) вашего приложения. Для продакшена минимальное значение для обеспечения высокой доступности — `2` (чтобы падение одного пода не уронило сервис).

- **`selector.matchLabels`**: Метки, по которым Deployment понимает, какими именно подами он управляет. Они должны строго совпадать с метками в шаблоне подов (`template.metadata.labels`).

### 2. Стратегия обновления (`spec.strategy`)

Определяет, как Kubernetes будет выкатывать новые версии приложения.

- **`type: RollingUpdate`** (по умолчанию): Самый безопасный метод. Новые поды поднимаются постепенно, а старые гасятся по мере готовности новых.

- Важные саб-параметры:

  - **`maxSurge`** — сколько дополнительных подов сверх нормы можно создать во время обновления (например, `25%` или `1`).

  - **`maxUnavailable`** — сколько максимум подов может быть выключено одновременно в процессе деплоя (например, `0` или `25%`).

### 3. Ресурсы контейнера (`resources: requests & limits`) — _Самый критичный параметр_

Никогда не оставляйте контейнеры без указания ресурсов, иначе один «поехавший» под может забрать всю память ноды и положить соседние приложения.

- **`requests`** (Запросы): Гарантированный минимум ресурсов, который Kubernetes выделяет под для запуска. Планировщик (`kube-scheduler`) ищет ноду, где есть свободные `requests`.

- **`limits`** (Лимиты): Максимальный предел ресурсов. Если контейнер превышает лимит по CPU, его начинают искусственно «тротлить» (замедлять). Если превышает лимит по RAM, ядро Linux мгновенно убивает процесс с ошибкой **OOMKilled** (Out Of Memory).

### 4. Пробы здоровья (`livenessProbe`, `readinessProbe`, `startupProbe`)

Эти параметры говорят Kubernetes, живое ли приложение и готово ли оно принимать трафик. Без них Kubernetes может отправить трафик на под, который еще не успел инициализироваться, или не перезапустить зависший сервис.

- **`readinessProbe`** (Проверка готовности): Проверяет, готов ли под принимать запросы (например, поднялась ли база данных внутри приложения). Если проверка падает, Kubernetes временно убирает под из Service, и трафик на него не идет.

- **`livenessProbe`** (Проверка жизни): Проверяет, не зависло ли приложение. Если проверка падает несколько раз подряд, Kubernetes принудительно убивает контейнер и создает его заново.

- **`startupProbe`** (Проверка старта): Используется для медленно запускающихся приложений (например, тяжелых монолитов), чтобы `livenessProbe` не убила под раньше времени.

### 5. Политика перезапуска и безопасность (`restartPolicy` & `securityContext`)

- **`restartPolicy`**: Для Deployment всегда используется значение **`Always`** (если контейнер падает или завершается, Kubernetes обязан его поднять).

- **`securityContext`**: Параметры безопасности. Золотое правило production — запускать контейнеры **не от имени суперпользователя (root)**, а также отключать эскалацию привилегий:

    ```YAML
    securityContext:
      runAsNonRoot: true
      runAsUser: 10001
      allowPrivilegeEscalation: false
    ```

### 6. Селекторы размещения (`nodeSelector`, `affinity`, `tolerations`)

Если вам нужно жестко зафиксировать, на каких именно нодах должен крутиться Deployment (например, отправлять тяжелые ML-задачи только на GPU-серверы или разносить поды по разным стойкам дата-центра для отказоустойчивости), используются правила селекции и антиаффинитета.

### Пример минимально правильного production-шаблона

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  strategy:
    type: RollingUpdate
    maxSurge: 1
    maxUnavailable: 0
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: web
        image: my-registry.com/app:v1.2.3
        resources:
          requests:
            memory: "256Mi"
            cpu: "200m"
          limits:
            memory: "512Mi"
            cpu: "500m"
        ports:
        - containerPort: 8080
        readinessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
        securityContext:
          runAsNonRoot: true
          allowPrivilegeEscalation: false
```
