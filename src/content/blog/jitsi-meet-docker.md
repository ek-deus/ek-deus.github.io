Jitsi Meet можно развернуть на собственном сервере и управлять доменом, доступом и данными самостоятельно. Официальный проект `docker-jitsi-meet` поставляет Docker Compose-конфигурацию и образы основных компонентов.

Ниже — базовая установка публичного Jitsi Meet на Linux-сервер. Это не готовая высокодоступная платформа: для первого запуска все компоненты размещаются на одном хосте. Разделы про обновление, NAT и доступ в комнаты важны и для production.

## Как устроен Jitsi Meet

Docker Compose поднимает несколько связанных сервисов. Веб-интерфейс и signaling идут через HTTPS и XMPP/WebSocket, а аудио и видео передаются напрямую через Jitsi Videobridge (JVB) по UDP. Поэтому работающий сайт ещё не означает, что медиасвязь настроена правильно.

```text
Браузер участников
    │
    ├── HTTPS / WebSocket ──> web ──> Prosody (XMPP signaling)
    │                            │             │
    │                            └──────────> Jicofo
    │                                          │
    └──────────── RTP / UDP :10000 ─────────> JVB
                                               │
                                      аудио и видео участников
```

Prosody отвечает за XMPP-сигнализацию, Jicofo координирует конференции, а JVB пересылает медиапотоки между участниками. Если JVB рекламирует недоступный адрес или UDP-порт закрыт, страница может открываться, но звонок не будет работать.

## Что подготовить

- Linux-сервер с Docker Engine и плагином Docker Compose v2;
- доменное имя, например `meet.example.com`, с A-записью на публичный IPv4-адрес сервера; для AAAA-записи IPv6 должен быть настроен полностью, включая UDP;
- входящие `80/tcp`, `443/tcp` и `10000/udp` на хостовом firewall и в сетевых правилах провайдера;
- ресурсы, подобранные под число участников и сценарий. Видеоконференции чувствительны к CPU и пропускной способности сети, поэтому не существует одной гарантированной конфигурации сервера для всех размеров встреч.

Проверьте Docker Compose:

```bash
docker --version
docker compose version
```

Если сервер находится за NAT, заранее выясните его внешний адрес и настройте port forwarding UDP 10000 на Docker-хост. HTTP reverse proxy не проксирует этот медиапоток.

## Получить стабильный релиз

Для обычной установки используйте архив опубликованного релиза `docker-jitsi-meet`, а не ветку `master`: `master` предназначен для работы с нестабильными образами. В production релиз следует зафиксировать и обновлять осознанно. Команды ниже получают tag последнего опубликованного GitHub-релиза; перед применением проверьте tag и закрепите выбранную версию в своём процессе выкладки.

```bash
mkdir -p "$HOME/jitsi-meet/releases"
cd "$HOME/jitsi-meet/releases"

RELEASE_TAG="$(curl --fail --silent --show-error --location \
  https://api.github.com/repos/jitsi/docker-jitsi-meet/releases/latest \
  | jq --raw-output --exit-status '.tag_name')"

curl --fail --silent --show-error --location \
  "https://github.com/jitsi/docker-jitsi-meet/archive/refs/tags/${RELEASE_TAG}.zip" \
  --output "docker-jitsi-meet-${RELEASE_TAG}.zip"

unzip -q "docker-jitsi-meet-${RELEASE_TAG}.zip"
cd "docker-jitsi-meet-${RELEASE_TAG}"
printf 'Selected docker-jitsi-meet release: %s\n' "$RELEASE_TAG"
```

Нужны `curl`, `jq` и `unzip`. После скачивания сохраняйте выбранный tag вместе с конфигурацией: не используйте обновление образов до произвольного `latest`.

## Создать `.env` и служебные пароли

Скопируйте шаблон и сгенерируйте отдельные случайные пароли для внутренних сервисных учётных записей:

```bash
cp env.example .env
./gen-passwords.sh
chmod 600 .env .env.bak
```

Скрипт обновляет `.env` и создаёт резервную копию `.env.bak`. Проверьте, что оба файла игнорируются Git, не добавляйте их в репозиторий и не переиспользуйте эти пароли в других системах.

Задайте основные переменные. Замените домен и адрес на значения своей инфраструктуры:

```dotenv
CONFIG=/opt/jitsi-meet-cfg
PUBLIC_URL=https://meet.example.com
TZ=Europe/Istanbul
JVB_ADVERTISE_IPS=203.0.113.10
```

`203.0.113.10` — адрес из документационного диапазона, это пример. Укажите реальный публичный адрес видеомоста, только если JVB находится за NAT или не может корректно определить адрес сам. Для нескольких сетей или split-horizon можно передать список адресов. При обычной публичной адресации переменную не задавайте без необходимости.

### Права на каталоги конфигурации

Начиная с релиза `stable-11146`, контейнеры запускаются от непривилегированного UID/GID `1000`, а их root filesystem работает в режиме read-only. До первого запуска создайте каталоги, указанные официальной конфигурацией:

```bash
CONFIG=/opt/jitsi-meet-cfg

sudo install -d -m 0755 \
  "$CONFIG/web" \
  "$CONFIG/prosody/config" \
  "$CONFIG/prosody/prosody-plugins-custom" \
  "$CONFIG/jicofo" \
  "$CONFIG/jvb" \
  "$CONFIG/jigasi" \
  "$CONFIG/jibri" \
  "$CONFIG/transcriber"

sudo install -d -o 1000 -g 1000 -m 0750 \
  "$CONFIG/storage/jibri" \
  "$CONFIG/storage/prosody" \
  "$CONFIG/storage/transcripts" \
  "$CONFIG/storage/web" \
  "$CONFIG/tmp/web-crontabs" \
  "$CONFIG/tmp/web-load-test"
```

В этом шаблоне каталоги постоянного состояния и временных файлов доступны на запись UID/GID `1000`, а не всем пользователям хоста. Не применяйте `chmod 777`. Остальные каталоги конфигурации контейнеры читают как входные файлы; если ваш владелец и группа отличаются, настройте чтение отдельно, не выдавая лишний доступ к `.env`.

Важно: размещайте `.env` и каталог `CONFIG` в постоянном хранилище. Внутри `storage` могут лежать состояние Prosody, TLS-материалы, записи и транскрипты. Каталог `tmp` находится на хосте и не очищается автоматически.

## Настроить HTTPS

Выберите один вариант: TLS завершается в контейнере Jitsi либо на внешнем reverse proxy. Не включайте одновременно два независимых владельца одного и того же публичного сертификата.

### Вариант 1: Jitsi принимает трафик напрямую

Если порты 80 и 443 свободны и DNS уже указывает на сервер, настройте встроенный выпуск Let’s Encrypt:

```dotenv
HTTP_PORT=80
HTTPS_PORT=443
ENABLE_HTTP_REDIRECT=1
ENABLE_LETSENCRYPT=1
LETSENCRYPT_DOMAIN=meet.example.com
LETSENCRYPT_EMAIL=admin@example.com
PUBLIC_URL=https://meet.example.com
```

Убедитесь, что внешние firewall и security group пропускают `80/tcp` и `443/tcp`. Не удаляйте конфигурационное хранилище с TLS-материалами при обычном обновлении: это может вызвать повторный выпуск сертификата и столкновение с rate limit.

### Вариант 2: перед Jitsi стоит Nginx или Traefik

В этом случае сертификат выпускает и обновляет proxy. В `.env` оставьте HTTP/HTTPS порты контейнерного endpoint по умолчанию (`8000` и `8443`) и задайте:

```dotenv
PUBLIC_URL=https://meet.example.com
DISABLE_HTTPS=1
ENABLE_HTTP_REDIRECT=0
ENABLE_LETSENCRYPT=0
```

В `docker-compose.yml` привяжите web-порты к loopback, например `127.0.0.1:${HTTP_PORT}:8000`; аналогично для HTTPS endpoint, если он нужен локально. Не оставляйте backend-порты доступными извне в обход proxy. Reverse proxy должен поддерживать WebSocket-маршрут `/xmpp-websocket`.

Reverse proxy обрабатывает веб-трафик и signaling, но медиапоток всё равно идёт к JVB напрямую по UDP. Поэтому настройка proxy не заменяет проброс `10000/udp` и корректное значение `JVB_ADVERTISE_IPS` при NAT.

## Запустить Jitsi и открыть необходимые порты

Проверьте итоговую Compose-конфигурацию, затем запустите базовый набор сервисов:

```bash
docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps
```

На UFW при прямом публичном доступе добавьте входящие правила для веб-интерфейса и видеомоста:

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 10000/udp
sudo ufw status
```

Повторите соответствующие правила в firewall облака или гипервизора. Если TLS завершает внешний proxy, порты `80/443` должны вести на proxy; web backend Jitsi ограничьте localhost или внутренней сетью. Порт `10000/udp` должен достигать именно хоста с JVB.

Откройте `https://meet.example.com` и проведите пробную встречу с двумя устройствами в разных сетях, например с компьютера и телефона через мобильную сеть. Это проверяет не только веб-доступ, но и медиа-трафик через NAT.

## Закрыть создание комнат для анонимных пользователей

Стандартная публичная установка может разрешать любому пользователю создавать комнату. Если конференции предназначены только вашей организации, включите аутентификацию в `.env` и используйте выбранный поддерживаемый механизм, например внутреннюю Prosody-аутентификацию или JWT:

```dotenv
ENABLE_AUTH=1
AUTH_TYPE=internal
```

Режим гостевого входа выбирайте отдельно: при включённом гостевом доступе неаутентифицированный участник должен ждать, пока в комнату войдёт аутентифицированный пользователь. Создавайте учётные записи через официальный процесс Prosody и защитите `.env`, особенно если используете JWT-секрет. Проверьте поведение анонимного пользователя после настройки: он не должен иметь возможность самостоятельно создать комнату.

## Опциональные компоненты

- **Jigasi** подключает SIP-телефонию. До его запуска задайте SIP-параметры и откройте нужный медиадиапазон, указанный в документации выбранного релиза.
- **Jibri** записывает или транслирует конференции. Он требует дополнительной подготовки хоста и ресурсов; включайте его только после настройки отдельной конфигурации.
- **Etherpad** добавляет совместное редактирование документов; это ещё один сервис и отдельная поверхность для обновлений и доступа.

Compose-файлы можно объединять. Пример совместного запуска Jigasi и Jibri:

```bash
docker compose \
  -f docker-compose.yml \
  -f jigasi.yml \
  -f jibri.yml \
  config --quiet

docker compose \
  -f docker-compose.yml \
  -f jigasi.yml \
  -f jibri.yml \
  up -d
```

Для каждого компонента сначала настройте переменные и требования к хосту по его официальной инструкции, затем откройте только необходимые ему порты.

## Если встреча не работает

| Симптом | Что проверить |
|---|---|
| Страница открывается, но нет аудио или видео | Входящий `10000/udp` до JVB, внешний адрес в `JVB_ADVERTISE_IPS`, NAT/port forwarding, публичный маршрут UDP |
| Участники видят друг друга только вдвоём или звонок рушится при подключении третьего | В первую очередь проверьте advertised IP видеомоста: JVB за NAT может объявлять внутренний адрес |
| Не выпускается сертификат Let’s Encrypt | A/AAAA-записи, доступность 80/443, занятые порты, корректность домена и сохранность каталога `CONFIG` |
| Контейнер сообщает о `Permission denied` или отсутствующем каталоге | Наличие всех путей `storage`/`tmp` и возможность записи UID/GID 1000 в нужные директории |
| Камера или микрофон недоступны | Пользуйтесь HTTPS с доверенным сертификатом; проверьте разрешения браузера и WebRTC |
| Нестабильная связь в корпоративной сети | Проверьте UDP-путь и рассмотрите отдельный TURN-сервер; настройте его по официальному руководству |

Логи основных компонентов доступны через Compose:

```bash
docker compose logs --since=10m web prosody jicofo jvb
```

Для диагностики WebRTC в Chromium можно использовать `chrome://webrtc-internals`. Перед публикацией логов или дампов проверьте их на токены, адреса участников и другие чувствительные данные.

## Обновлять отдельным релизом

Не скачивайте новый релиз поверх рабочей папки без сохранения исходного состояния. Безопаснее хранить каталоги версий отдельно и сохранять стабильный путь к конфигурации:

1. Зафиксируйте текущий tag образов и сделайте резервную копию `.env`, `CONFIG`, Prosody state и записей Jibri.
2. Получите новый опубликованный релиз в новый каталог, а не заменяйте текущий.
3. Сравните новый `env.example` со своим `.env`, внесите новые обязательные параметры и проверьте release notes.
4. Проверьте Compose-рендер командой `docker compose config --quiet`, скачайте образы и выполните `docker compose up -d`.
5. Проверьте `docker compose ps`, логи, а затем тестовую конференцию с двух сетей.
6. Удаляйте старый релиз только после успешной проверки и подтверждённой резервной копии.

При переходе с релиза до `stable-11146` изменились права и расположение части каталогов из-за rootless-контейнеров и read-only filesystem. Следуйте миграционным шагам именно для исходной и целевой версий; отдельно проверьте перенос записей и транскриптов. Не применяйте `docker compose down -v` как штатный шаг обновления: удаление volumes может уничтожить данные.

## Итог

Для базового self-hosted Jitsi достаточно Compose-релиза, домена, HTTPS и правильно доступного видеомоста. Критичная часть сетевой настройки — не только открыть веб-порты, но и обеспечить достижимость JVB по UDP с корректно объявленным адресом. Перед публикацией также решите, кто может создавать комнаты, и сохраните `.env` с паролями вне Git.

Перед обновлением или подключением дополнительных компонентов сверяйте параметры с [официальным руководством Jitsi для Docker](https://jitsi.github.io/handbook/docs/devops-guide/devops-guide-docker/), [разделом про аутентификацию](https://jitsi.github.io/handbook/docs/devops-guide/devops-guide-docker/#authentication), [запуском за NAT](https://jitsi.github.io/handbook/docs/devops-guide/devops-guide-docker/#running-behind-nat-or-on-a-lan-environment) и [руководством по TURN](https://jitsi.github.io/handbook/docs/devops-guide/turn/).
