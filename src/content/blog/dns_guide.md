**DNS (Domain Name System)** - распределённая система, которая по имени домена сообщает, где находится сайт, куда доставлять почту и кому принадлежит домен. Каждый такой ответ хранится в зоне домена в виде записи определённого типа. 

Эта статья - подробный справочник по типам записей. Как настраивать DNS для сайта и почты по шагам, разобрано в цикле «Настройка DNS для почты и сайта»: основные записи A и MX, SPF, DKIM и DMARC, настройка и проверка, BIMI.

---

## Два принципа: TTL и делегирование

### TTL - время жизни записи в кеше

У каждой записи есть TTL (Time-to-Live) - число секунд, в течение которого резолверы и клиенты могут хранить ответ, не отправляя повторный запрос.

| TTL | Плюсы | Минусы |
| :--- | :--- | :--- |
| **Низкий** (300 с, 5 мин) | Изменения расходятся быстро | Больше запросов к DNS-серверам |
| **Высокий** (86 400 с, сутки) | Меньше запросов, ответы стабильны | Изменения применяются медленно |

Для стабильных записей (A, MX) обычно ставят от часа до суток. Перед переездом TTL заранее снижают (подробнее см. в разделе «TTL при переезде» ниже).

### Делегирование и NS-серверы

Родительская зона (например, `.ru` или `.com`) передаёт управление вашей зоной `example.ru` серверам, указанным в записях NS. 

Серверов должно быть **не меньше двух**, желательно в разных сетях: этого требует RFC 2182 и правила большинства регистраторов. Если один сервер перестанет отвечать, резолверы автоматически обратятся к другому.

## Базовые записи

| Запись | Что делает | Пример |
| :--- | :--- | :--- |
| **A** | Сопоставляет имя с IPv4-адресом | `example.ru. A 192.0.2.1` |
| **AAAA** | Сопоставляет имя с IPv6-адресом | `example.ru. AAAA 2001:db8::1` |
| **CNAME** | Псевдоним: имя указывает на другое имя | `blog.example.ru. CNAME hosting.example.net.` |
| **MX** | Почтовый сервер домена и его приоритет | `example.ru. MX 10 mx.yandex.net.` |

> **Важное ограничение:** У имени с CNAME не может быть никаких других записей (согласно RFC 1034 и RFC 2181). Именно поэтому CNAME **нельзя поставить на корень домена** (`example.ru`), так как там всегда присутствуют обязательные записи SOA и NS.

## Служебные записи

### NS - серверы, отвечающие за зону
NS-записи присутствуют в двух местах: у регистратора (в родительской зоне - это и есть делегирование) и внутри самой зоны. Они должны строго совпадать: любые расхождения приводят к тому, что часть глобальных резолверов будет получать устаревшие ответы.

### SOA - параметры зоны
Существует ровно одна запись SOA на зону. Она описывает основной сервер, контактный адрес администратора и таймеры обновления для вторичных серверов.

```dns
example.ru. IN SOA ns1.example.ru. admin.example.ru. (
    2025111101   ; Serial (ГГГГММДДNN)
    7200         ; Refresh - как часто вторичные серверы проверяют зону
    3600         ; Retry - повтор при неудаче
    1209600      ; Expire - когда вторичный сервер перестаёт отвечать без связи с основным
    86400        ; Minimum - TTL отрицательных ответов (RFC 2308)
)
```

Серийный номер (`Serial`) необходимо увеличивать при каждом изменении зоны, иначе вторичные серверы не заберут обновления. Формат `ГГГГММДДNN` (дата и порядковый номер правки за день) очень удобен, но не является жестким требованием. У современных облачных DNS-провайдеров SOA обычно генерируется и поддерживается автоматически.

### TXT - произвольный текст
Широко используется для настройки SPF, DKIM, DMARC-политик и подтверждения прав на владение доменом:

```dns
example.ru. TXT "v=spf1 mx include:_spf.yandex.net -all"
example.ru. TXT "yandex-verification=abc123"
_dmarc.example.ru. TXT "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.ru"
```

> Подробно о почтовых записях рассказано во второй части цикла по настройке DNS.

### CAA - кому разрешено выпускать сертификаты
Запись ограничивает список центров сертификации (CA), которые имеют право выпускать TLS-сертификаты для вашего домена (RFC 8659):

```dns
example.ru. CAA 0 issue "letsencrypt.org"
```

Если CAA-записей в зоне нет, выпускать сертификаты для вашего домена может абсолютно любой центр сертификации.

### PTR - обратная запись (Reverse DNS)
Сопоставляет IP-адрес обратно с доменным именем. Хранится в специальной зоне `in-addr.arpa` (для IPv4) и настраивается непосредственно у владельца пула IP-адресов - как правило, у вашего хостинг-провайдера. 
* Для почтового сервера наличие корректного PTR **обязательно**: без него письма будут массово уходить в спам.

### SRV - сервер и порт службы
SRV-запись сообщает клиентам, на каком хосте и порту запущена конкретная служба:

```dns
_minecraft._tcp.play.example.ru. IN SRV 10 5 25565 mc.example.ru.
```

* **Приоритет (10):** чем меньше число, тем важнее сервер.
* **Вес (5):** используется для распределения нагрузки между серверами с одинаковым приоритетом.
* **Порт (25565):** сетевой порт службы.
* **Хост (`mc.example.ru`):** целевой сервер.

SRV-записи активно используются протоколами SIP, XMPP, Kerberos, LDAP в Active Directory, а также некоторыми многопользовательскими играми.

## ALIAS (ANAME) и CNAME на корне домена

Техническое ограничение CNAME сильно мешает, когда корневой домен (`example.ru`) необходимо направить на внешнее доменное имя платформы (например, на балансировщик облачного провайдера). Современные DNS-провайдеры обходят это ограничение фирменными решениями: они сами резолвят целевое имя на своей стороне и отдают клиенту готовые A/AAAA-записи.

| Провайдер | Название функции | Описание |
| :--- | :--- | :--- |
| DNSimple и др. | **ALIAS** или **ANAME** | Прямой аналог для корня зоны |
| Cloudflare | **CNAME flattening** | Разрешает CNAME на корне домена |
| AWS Route 53 | **Alias** | Ссылается на ресурсы AWS или другие записи зоны |

> Важно помнить, что это не стандартный тип записей из официальных RFC, а проприетарная функция конкретного DNS-провайдера. При миграции к другому регистратору её потребуется настраивать заново.

## GeoDNS - технология, а не тип записи

GeoDNS отвечает на запросы по-разному в зависимости от географического происхождения клиента: пользователям из Европы отдается адрес европейского сервера, а из Азии - азиатского. 

Геолокация определяется по IP-адресу резолвера или подсети клиента, если резолвер поддерживает технологию EDNS Client Subnet (RFC 7871). Подобную интеллектуальную маршрутизацию предлагают многие современные CDN и DNS-провайдеры (например, Route 53 Geolocation Routing).

## Прочие типы записей

| Запись | Назначение |
| :--- | :--- |
| **DS / DNSKEY** | Настройка DNSSEC: организация цепочки доверия от родительской зоны и криптографические ключи подписи. |
| **NAPTR** | Правила преобразования адресов, активно используется в телефонии (SIP, ENUM). |
| **HTTPS / SVCB** | Параметры подключения к сервису (например, поддержка HTTP/3) еще до установки соединения (RFC 9460). |

## Как проверить DNS-записи

Для диагностики используется утилита `dig`:

```bash
dig NS example.ru +trace           # Проверка делегирования от корня до ваших NS
dig A example.ru                   # Получение A-записи сайта
dig MX example.ru                  # Проверка почтовых серверов
dig TXT example.ru                 # Проверка SPF-политик и подтверждений
dig TXT _dmarc.example.ru          # Проверка DMARC
dig SOA example.ru                 # Просмотр параметров зоны и серийного номера
dig CAA example.ru                 # Проверка разрешённых центров сертификации
dig -x 192.0.2.1                   # Обратная PTR-запись для IP-адреса
dig example.ru +dnssec             # Проверка цифровых подписей DNSSEC
```

> **Совет:** Чтобы опросить конкретный авторитативный сервер напрямую, а не брать данные из кеша локального резолвера, явно укажите его через символ `@`:
> `dig A example.ru @ns1.example.ru`

## TTL при переезде

Если вы планируете смену IP-адреса или перенос домена, подготовьтесь заблаговременно:

1. **За двое суток** (или за время, не меньшее вашего текущего TTL) снизьте TTL переносимых записей до `300` секунд (5 минут).
2. **Дождитесь истечения старого TTL** - только после этого все промежуточные резолверы в интернете начнут запрашивать данные чаще.
3. **Произведите замену записей** у провайдера.
4. После успешной проверки работоспособности на новом месте **верните TTL** к стандартным значениям (от часа до суток).

## Итог

DNS - это фундамент, на котором держится доступность сайта, почты и корпоративных сервисов. Понимание назначения каждой записи, умение правильно использовать TTL, настраивать делегирование и проводить диагностику с помощью `dig` избавляет администратора от львиной доли потенциальных проблем в инфраструктуре.
