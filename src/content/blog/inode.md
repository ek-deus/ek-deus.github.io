Краткий ответ

Новые файлы и каталоги создать нельзя — ОС вернёт ошибку 'No space left on device', хотя `df -h` покажет свободное место. Диагностика: `df -i`. Inode — это метаданные файла (права, владелец, размер, указатели на блоки), но не само содержимое. Количество inode фиксируется при форматировании.

Каждый файл и каталог потребляет ровно один inode. Таблица inode создаётся при `mkfs` с фиксированным размером (по умолчанию 1 inode на каждые 16 КБ блокового пространства для ext4). Если inode исчерпаны — запись любых новых файлов невозможна, даже если на диске гигабайты свободны.


```
df -i # IUse% = 100% — диагноз поставлен
df -ih /var # конкретная ФС-виновник
find /var -xdev -printf '%h\n' | sort | uniq -c | sort -rn | head -20
# ^^^ находим каталог с огромным числом файлов
```

Типичные причины: спам мелкими файлами в `/tmp`, `/var/spool/postfix`, очереди задач, неочищаемые PID-файлы, тысячи пустых лог-файлов. Решение: удалить мусорные файлы, либо пересоздать ФС с меньшим `bytes-per-inode` (`mkfs.ext4 -i 4096 /dev/sdX`). Для ext4 можно посмотреть текущий ratio: `tune2fs -l /dev/sdX | grep 'Inode ratio'`.

Ключевые тезисы

- Inode = метаданные файла; данные файла — отдельно, в блоках
- Количество inode фиксировано при создании ФС (mkfs)
- `df -i` — диагностика; IUse% = 100% = нельзя создать новый файл
- Ошибка внешне неотличима от 'нет места' — ENOSPC в обоих случаях
- find по числу файлов в каталоге — быстрый способ найти виновника

Частые ошибки

- ✕Смотреть только `df -h` и делать вывод, что места достаточно
- ✕Не знать команду `df -i`
- ✕Думать, что inode можно добавить без пересоздания ФС (для ext4 — нельзя)

Краткий ответ

Да. Linux удаляет только directory entry, но inode и блоки данных живут, пока есть открытые file descriptor-ы. Восстановление: `lsof | grep deleted` → узнаём PID и номер FD → `cp /proc/<pid>/fd/<fd_num> /restored_config`. Пока процесс жив — файл можно восстановить точно.

Системный вызов `unlink()` (который выполняет `rm`) удаляет **ссылку** из каталога, но inode уничтожается ядром только когда link count = 0 **и** нет открытых FD. Пока процесс держит файл открытым — он живёт в `/proc/<pid>/fd/`.


```
lsof | grep deleted # найти PID и FD номер
ls -la /proc/<pid>/fd/ # список всех открытых FD процесса
cp /proc/<pid>/fd/<fd> /etc/restored.conf # восстановить
```

Параллельный эффект: `df` покажет, что место НЕ освободилось после `rm`. Освобождение произойдёт только после закрытия всех FD (выход процесса или явный `close`). Именно поэтому `df` и `du` могут расходиться.

Для логов без перезапуска сервиса используем `truncate -s 0 /path/to/log` — это обнуляет файл на месте, FD остаётся валидным. `rm` + `touch` так не работает: процесс продолжит писать в старый (unlinkd) inode.

Ключевые тезисы

- `rm` = unlink directory entry; inode жив, пока есть открытые FD
- Восстановление: `cp /proc/<pid>/fd/<fd> <destination>`
- `lsof | grep deleted` показывает процессы с открытыми удалёнными файлами
- Место на диске не освобождается до закрытия последнего FD
- `truncate -s 0` обнуляет файл без unlink — FD остаётся валидным

Частые ошибки

- ✕Думать, что `rm` немедленно освобождает место
- ✕Не знать `/proc/<pid>/fd/` как механизм восстановления
- ✕Путать `truncate` и `rm` при ротации логов без рестарта
- ✕Думать, что восстановление возможно после завершения процесса
